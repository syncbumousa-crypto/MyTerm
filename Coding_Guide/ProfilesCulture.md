# الحسابات وبيانات المستخدمين في المواقع الثابتة

## 1) فكرة السيرفر

**السيرفر حاسوب يعمل دائمًا، ينتظر طلبات ويجيب عليها.** لا أكثر. والفرق بينه وبين حاسوب المستخدم أنه لا يُغلَق، وله عنوان ثابت على الإنترنت.

```
متصفّح الزائر  ──  طلب   ──►  السيرفر
   (العميل)    ◄──  جواب  ──
```

| نوع السيرفر | ماذا يفعل |
|---|---|
| **سيرفر ملفات** (استضافة ثابتة) | يسلّم الملف كما هو: HTML و CSS و JS وصور. **لا يُشغّل شيئًا** |
| **سيرفر تطبيقات** (الخلفية) | **يُشغّل كودًا** عند كل طلب: يتحقق، ويحسب، ويكلّم قاعدة البيانات |

والسطر الحاكم لكل ما بعده:

> **كل ما في الصفحة تحت سيطرة الزائر.** يفتح `F12` فيقرأ الكود كله، ويعدّله، ويرسل ما يشاء. فما يحتاج سرًّا أو قرارًا نهائيًّا **لا يُنفَّذ في المتصفّح**، بل في موضع لا يملكه الزائر.

ولهذا لا تُكتب الحسابات في JavaScript وحده: ليس لأن الكود يعجز، بل لأن الزائر يستطيع تغييره.

## 2) ما قاعدة البيانات

**برنامج يحفظ البيانات منظَّمة، ويجيب على أسئلة عنها.** لا يُفتح كملف، بل يُسأل فيُجيب.

وتنظيمها في **جداول**: الجدول موضوع واحد، والصف سجل واحد، والعمود حقل.

| id | email | created_at |
|---|---|---|
| 1 | a@x.com | 2026-01-05 |
| 2 | b@x.com | 2026-02-11 |

ويُسأل بلغة استعلام. في Postgres لغته SQL:

```sql
SELECT email FROM users WHERE id = 2;
```

**ولماذا لا يكفي ملف:**

| | |
|---|---|
| **البحث** | الملف يُقرأ من أوله. والقاعدة تبني **فهرسًا** فتجد السجل في مليون سجل فورًا |
| **الكتابة المتزامنة** | لو كتب مستخدمان في ملف واحد في اللحظة نفسها، ضاع أحدهما. والقاعدة تنظّم التزامن |
| **السلامة** | تمنع بريدًا مكرَّرًا، وتمنع سجلًّا ناقص الحقول، قبل أن يُكتب |

> ومنها نوع ثانٍ لا جداول فيه بل **مستندات** — مثل Firestore — تُحفظ فيه البيانات ككائنات متداخلة. والفكرة واحدة: تُسأل فتجيب.

## 3) لماذا لا تُخزَّن البيانات في مستودع الكود

| | |
|---|---|
| **الكشف** | المستودع العامّ يقرؤه كل أحد، وتُفهرسه محركات البحث |
| **لا طريق للكتابة** | الصفحة تعمل في متصفّح الزائر ولا تملك صلاحية على المستودع، فلا تصل بيانات التسجيل إليه |
| **Git ليس قاعدة بيانات** | لا فهرس، ولا استعلام، ولا كتابة متزامنة |

## 4) حدود الاستضافة الثابتة

تُقدّم الملفات ولا تُشغّلها. فـ JavaScript يعمل لأنه يُنفَّذ في متصفّح الزائر، وما يحتاج الخادم لا يعمل.

| يعمل | لا يعمل |
|---|---|
| أزرار، ونماذج، وحفظ في المتصفّح | قاعدة بيانات، وحسابات، وإرسال بريد |

## 5) الحل: خدمة وسيطة

**الصفحة تبقى ثابتة، والسيرفر وقاعدة البيانات يُستأجران جاهزين.** فلا سيرفر يُدار، ولا بيانات في المستودع.

| الخدمة | ما تعطي |
|---|---|
| **Supabase** | حسابات + قاعدة بيانات Postgres + صلاحيات |
| **Firebase** | حسابات + قاعدة بيانات مستندات، من Google |
| **Clerk** | حسابات فقط، بلا قاعدة بيانات |

## 6) ماذا يحدث عند إنشاء الحساب

```
①  الزائر يكتب بريدًا وكلمة سر في النموذج
②  الصفحة ترسلهما إلى الخدمة عبر HTTPS       ← مشفَّران في الطريق
③  الخدمة تتحقق أن البريد غير مستعمل
④  الخدمة تحوّل كلمة السر إلى بصمة            ← لا تحفظها نصًّا
⑤  تُنشئ صفًّا جديدًا في جدول المستخدمين
⑥  قد ترسل بريد تأكيد                        ← حسب الإعداد
⑦  تُعيد للصفحة رمز دخول
⑧  الصفحة تحفظ الرمز في المتصفّح
```

### عن البصمة في ④

**تحويل في اتجاه واحد لا يُرَدّ إلى أصله.** تُدخَل كلمة السر في دالة (مثل bcrypt أو argon2) فتخرج سلسلة لا تشبهها، والعملية العكسية غير ممكنة.

ويُضاف إليها **ملح**: قيمة عشوائية لكل مستخدم، تُخلط بكلمة السر قبل البصم. فلو اتفقت كلمتا سر لمستخدمين، اختلفت بصمتاهما.

> **ولهذا لا تستطيع أي خدمة أن تخبرك بكلمة سرك**، وإنما تعرض إعادة تعيينها. ومن أخبرك بها فهو يحفظها نصًّا، وذاك عيب جسيم.

### عن الرمز في ⑦

**رمز موقَّع يحمل هوية المستخدم وتاريخ انتهاء** (الشائع صيغة JWT). والتوقيع يجعل الخدمة تتحقق أنه لم يُعدَّل، فلا يستطيع الزائر تغيير الهوية فيه.

| | |
|---|---|
| **رمز الوصول** | قصير العمر، دقائق أو ساعة. يُرسَل مع كل طلب |
| **رمز التجديد** | أطول عمرًا. يُجدِّد الأول بلا إعادة تسجيل دخول |

وقِصَر عمر الأول مقصود: لو سُرق، فمدة نفعه قصيرة.

## 7) ماذا يحدث عند تسجيل الدخول

```
①  الزائر يكتب بريدًا وكلمة سر
②  الصفحة ترسلهما عبر HTTPS
③  الخدمة تجد الصف بالبريد
④  تبصم كلمة السر المُدخَلة بالملح نفسه
⑤  تقارن البصمتين                          ← لا تفكّ المحفوظة
⑥  تطابقتا ← رمز دخول   |   لا ← خطأ
```

**والخطوة ⑤ هي الفكرة:** لا تُفَكّ البصمة المحفوظة أبدًا. تُبصَم المُدخَلة وتُقارَن البصمتان. فالخدمة تعرف أن كلمة السر صحيحة **دون أن تعرف كلمة السر**.

> ورسالة الخطأ تُصاغ غامضة: «البريد أو كلمة السر خطأ» لا «كلمة السر خطأ». فالثانية تكشف أن هذا البريد مسجَّل، وهذه معلومة تُستغَلّ.

## 8) كيف تُجلب البيانات بعد الدخول

```
الصفحة ──► طلب + رمز الدخول ──► الخدمة
                                  │
                                  ├─ ① هل الرمز صحيح وغير منتهٍ؟
                                  ├─ ② قواعد الصلاحيات: ماذا يحق لهذا المستخدم؟
                                  └─ ③ استعلام القاعدة بما يحق له
الصفحة ◄── JSON ◄─────────────────┘
الصفحة ترسم البيانات في العناصر
```

والطلب يُكتب بمكتبة الخدمة، بلا SQL في الصفحة:

```js
const { data } = await db.from('notes').select('*');
```

والنتيجة **JSON**: صيغة نصّية تحمل البيانات، تحوّلها JavaScript إلى كائنات ثم تضعها في الصفحة.

### قواعد الصلاحيات

وهي الخطوة ② وأهم ما في الباب. تُكتب **على الجدول في لوحة الخدمة**، لا في الصفحة. ومعناها شرط يُلزَق بكل استعلام:

> «في جدول الملاحظات، يُسمح للمستخدم بقراءة الصفوف التي عمود `user_id` فيها يساوي معرّفه، لا غير.»

فلو طلبت الصفحة كل الصفوف، أعادت الخدمة صفوفه وحدها — **ولو عدّل الزائر كود الصفحة**. اسمها في Postgres و Supabase: **Row Level Security**، وفي Firebase: **Security Rules**.

**وبلا هذه القواعد، الجدول مفتوح لكل من يملك المفتاح العامّ.** وهذا أشهر خطأ في هذا الباب.

## 9) كيف يرتبط موقع ثابت بقاعدة بيانات في خدمة أخرى

**لا شيء يُنصَّب، ولا قاعدة تُنسَخ.** القاعدة تبقى على خوادم الخدمة، والارتباط ثلاثة أشياء فقط:

| | |
|---|---|
| **عنوان** | رابط HTTPS للخدمة |
| **مفتاح عامّ** | يُعرِّف المشروع |
| **إذن** | الخدمة تسمح لنطاق الموقع أن يكلّمها |

```
متصفّح الزائر                          خوادم الخدمة
┌────────────────────┐                ┌──────────────────┐
│  صفحة ثابتة        │                │  تحقّق الرمز       │
│  من GitHub Pages   │ ──HTTPS──────► │  قواعد الصلاحيات  │
│  + العنوان والمفتاح │ ◄─────JSON──── │  قاعدة البيانات   │
└────────────────────┘                └──────────────────┘
      نطاق أول                              نطاق ثانٍ
```

**وهو طلب شبكة عادي**، من جنس تحميل صورة من موقع آخر. ولا علاقة له بمستضيف الصفحة: الصفحة نفسها لو فُتحت من أي مكان، كلّمت الخدمة نفسها.

### CORS

وبقي قيد واحد يسأل عنه كثيرون. المتصفّح يمنع افتراضيًّا أن يطلب نطاقٌ بياناتٍ من نطاق آخر، حمايةً للمستخدم.

فتُعلِن الخدمة في جوابها أنها تسمح للنطاق الطالب، فيُمرِّر المتصفّح الجواب. **وهو إعداد في لوحة الخدمة: يُضاف نطاق الموقع إلى المسموح.** ولو نُسي، فشلت الطلبات ولم تظهر رسالة على الصفحة — ويكشفها `Console` و `Network` في `F12`.

## 10) لماذا لا يُؤتمَن المتصفّح

| يُنفَّذ في الصفحة | يُنفَّذ في الخدمة |
|---|---|
| التحقق من شكل البريد وطول كلمة السر | **التحقق النهائي من كل شيء** |
| إخفاء زر أو صفحة عن غير المسجَّل | **منع الوصول إلى البيانات** |
| رسائل الخطأ للمستخدم | **قواعد الصلاحيات** |

**وما في الصفحة للراحة لا للأمان.** إخفاء زر لا يمنع من يعرف العنوان، والتحقق في الصفحة يُتجاوَز بتعديل الكود.

> **والقاعدة:** كل تحقّق في الصفحة يجب أن يُكرَّر في الخدمة. والذي في الصفحة يوفّر على المستخدم طلبًا فاشلًا، والذي في الخدمة هو الذي يحمي.

## 11) أمان المفاتيح

| | |
|---|---|
| `anon public` | ✅ في الكود، سليم بتصميمه. مقيَّد بقواعد الصلاحيات |
| `service_role` | ❌ لا يدخل مستودعًا عامًّا، ولا صفحة تُحمَّل في متصفّح. يتجاوز كل القواعد |

**فالأمان في قواعد الصلاحيات لا في إخفاء المفتاح العامّ.** ولو غابت لم يحمِ المفتاح شيئًا.

## 12) ما يلزم للتنفيذ

| | |
|---|---|
| ملف `.js` | الاتصال بالخدمة، ومعالجة التسجيل والدخول وجلب البيانات |
| صفحتان | نموذج إنشاء الحساب، ونموذج الدخول |
| حساب على الخدمة | ومنه `Project URL` و `anon public key` |
| جدول للمستخدمين | وما يلزم من جداول البيانات |
| **قواعد صلاحيات** | **تُضبط قبل إدخال أي بيانات حقيقية** |
| نطاق الموقع | يُضاف إلى المسموح في إعداد CORS |
